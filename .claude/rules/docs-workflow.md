# 문서 워크플로우 (기획 → 프론트 → 백엔드)

`docs/` 는 전역 공통(`0-shared`) + 기능별 3단계(`1-feat`→`2-web`→`3-api`)로 구성된다. 무거운 산출물(ADR/RFC/DDD 도메인/API 계약 폴더/스키마/런북)은 두지 않는다.

```
docs/
├── 0-shared/ # 전역 공통 (용어집·공통 API 규약) — 단계 아님, 모든 단계가 참조
├── 1-feat/   # 무엇을, 왜
├── 2-web/    # 어떻게 보이나 (+ 백엔드에 필요한 API 정의)
└── 3-api/    # 어떻게 동작하나
```

## 규칙

1. **파일명 = 영문 kebab 슬러그.** 한 기능은 세 폴더에서 **같은 슬러그**를 쓰고 상호 링크로 연결한다 (`1-feat/user-login.md` → `2-web/user-login.md` → `3-api/user-login.md`). 1:N(기획 1개 → API 2개)은 링크로 표현한다.
2. **단계 순서를 지킨다.** 기획 없이 설계 시작 X. 단, **해당 없는 단계는 건너뛴다** — UI 없는 기능(크론잡·마이그레이션·CLI)은 `2-web`를 생략하고 `1-feat → 3-api`.
3. **경량 모드.** 소규모 기능은 단계를 나누지 말고 `1-feat/<슬러그>.md` 한 장에 인라인으로.
4. **새 문서는 해당 폴더의 `_template.md` 복사로 시작.** 복사 후 템플릿의 `<기능명>` 링크를 실제 슬러그로 치환한다.
5. **상호 참조는 상대 경로.** 단계 문서를 서로 링크로 연결한다.
6. **공통은 `0-shared`로.** 용어·공통 API 규약·인증은 `0-shared`에 한 번만 적고 기능 문서는 링크 참조 (반복 금지). 공유 데이터 모델은 둘 이상 기능이 같은 엔티티를 쓰게 될 때 `0-shared/data-model.md`로 추출(그 전엔 기능별 `3-api`에).
7. **다이어그램은 Mermaid만.** Figma/이미지 금지.
8. **미결정 값은 `{UNSET}`** (또는 `{UNSET: 설명}`). `[예: ...]` 패턴 금지 — AI가 실제 값으로 오해한다.
9. **frontmatter는 최소로**: `status`(draft|review|approved), `updated`.
10. **비-웹 프로젝트**: `2-web`=클라이언트/표면 설계, `3-api`=내부/처리 설계로 읽는다.

## 프론트 ↔ 백엔드 계약

프론트엔드 설계의 "API 연동" 표가 곧 백엔드 설계의 입력이다. 프론트가 필요로 하는 엔드포인트를 먼저 적고, 백엔드 문서에서 구현 관점으로 확정한다.
